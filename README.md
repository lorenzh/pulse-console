# pulse-console

pulse: Web console to manage checks, incidents, tokens, notify and status settings through the pulse-api admin API.

## What works now

The console is the fifth service of the pulse Compose stack. Today it serves:

- first-run setup: a one-time setup code from the container log unlocks `/setup/owner`. That page tests the connection to pulse-api (wire version and check count) and creates the one owner account in a local SQLite database;
- password sign-in for the owner, then a required second factor: a TOTP authenticator app (RFC 6238) or one of ten single-use recovery codes. A full session ends after 30 days without use; a signed-in shell with navigation, the Overview and sign-out. The Overview shows the overall state and six tiles: five state tiles (Down, Degraded, Unknown, Maintenance, Up) that link to `/checks?state=<state>`, and Total, which links to the unfiltered `/checks`. A tile with count `0` is still shown. With zero checks, no token, a rejected token or a failed read there are no tiles. On a wide screen the navigation is a left sidebar; at 719 px or less it is one row of links with icons that scrolls sideways (detail in `docs/configuration.md`). When pulse-api cannot be reached, the Overview names the kind of failure: `Kind: timeout`, `Kind: connection refused`, `Kind: network error` or `Kind: status <n>` (texts in `docs/configuration.md`);
- enrolment of the authenticator at `/account/authenticator` right after setup, with the setup key shown as text (no QR code), and replacement of it with the current password;
- the account security page `/account/security` (linked from the shell): new recovery codes with the current password, the list of signed-in sessions, and "Sign out all other sessions". The account security page, Sessions and both confirmations are signed-in shell pages with the header and the Main navigation, whose "Overview" link leads back to `/`; Sessions links "Back to account security", and both confirmations have a Cancel link (to `/account/sessions` and `/account/security`) that changes nothing; a signed-in unknown path shows the shell page `Page not found` with `There is no page at this address; go to the overview.` and a link to the overview;
- a single-use form token on every POST form, including the account and second-factor forms: a form sent twice changes nothing the second time;
- the stylesheet `/console.css`, the busy-button script `/console.js`, the seven font files under `/fonts/` and the ops routes `/healthz`, `/readyz` and `/metrics`.

Each person has one console role: Owner, Admin, Member or Viewer. The role is read from the database on every request, and a policy decides what each role may do; the Team page (`/team`, Admin and Owner) lists everyone and the pending invites, makes single-use invite links, and links to each person's role change, 2FA reset, removal and (for the Owner) ownership transfer; the Owner also turns the organisation-wide 2FA requirement on or off there (no email is sent; the person who made the link passes it on). Roles, the matrix, invites and the two-factor rule are in [docs/team.md](docs/team.md). In loopback mode an invite link starts with `http://<Host>` of the page that made it, so the invitee must open the console on a loopback address (the same machine or an SSH tunnel), or the operator sets `PULSE_CONSOLE_PUBLIC_URL`. An Admin (or the Owner, for an Admin) makes a single-use password reset link that works for 24 hours; everyone changes their own password at `/account/password`. The Owner recovers a lost password with the container command below. Passkeys are not part of the console yet. The Checks list (`/checks`, every role) shows the checks of pulse-api with their type, target, source, state and last result, filters them in the URL, and lets a Member or higher download a redacted export (`/checks/export`). The check detail (`/checks/check?id=<id>`) shows settings with readable labels, state, locations, uptime, latency (HTTP), recent results (one row per result, times with milliseconds) and the shell lines to copy; its heartbeat line holds the placeholder `<pulse-api-url>` instead of the saved API URL; a definition shadowed by `checks.json` has its own page (`/checks/shadowed?id=<id>`). The rules are in [docs/checks.md](docs/checks.md). A Member or higher creates a check of any of the six types at `/checks/new` and edits a Console check at `/checks/edit?id=<id>`; an edit keeps every field it does not change, including JSON pointers with spaces, and the editors work by keyboard with a visible focus outline and fit a 1280 px window; an Admin or higher deletes one at `/checks/delete?id=<id>`. The shell navigation links to Checks for every role. An Admin or the Owner manages the admin-side tokens of pulse-api at `/tokens`: the list with source, state and last use, create from a preset with the secret shown once, rotate with the overlap that pulse-api returns, and revoke after typing the name; the console's own token (from `GET /admin/tokens/self`) has no action. The Probes page (`/probes`, Admin and Owner) lists the probe locations with their state and every credential, adds a location and shows the env command, `docker run`, Compose file and Compose command once, and rotates or revokes one credential (revoke after typing the location). The rules are in [docs/tokens.md](docs/tokens.md). The Owner edits the status page settings of pulse-api at `/status-page`: name, logo URL, the 25 theme tokens, the four switches and the component order (Move up, Move down and Reset order buttons, no script needed); fields that pulse-status sets locally are read-only. The Owner manages the database notification channels of pulse-api at `/notifications`: the list shows database channels, shadowed copies (Delete only) and the file channels that pulse-notify reported (read-only); `/notifications/new`, `/notifications/edit?id=<id>` and `/notifications/delete?id=<id>` create, edit and delete a webhook, Slack, Teams or email channel whose secrets are reference names only; `/notifications/failed` lists up to 200 failed deliveries with a Resend button, and `/notifications/resend?id=<command id>` shows the state of a resend. Update the console before you give pulse-notify its token. See [docs/configuration.md](docs/configuration.md). The Incidents list (`/incidents`, every role) shows manual and automatic incidents with MTTR; a Member or higher publishes, updates and resolves a manual incident with a status-card preview (the preview shows the title heading only once the title is not empty), and an Admin or higher deletes one after typing its name. The rules are in [docs/incidents.md](docs/incidents.md). The Maintenance list (`/maintenance`, every role) shows current, planned, past and shadowed windows; a Member or higher plans and edits a database window in UTC, and an Admin or higher deletes one. The rules are in [docs/maintenance.md](docs/maintenance.md).

The Tokens and Probes pages show their banners and notices as the same callouts as the other pages: an error for a refusal or a failed read, a warning for the expiry of the last admin token, a location without an active token, an expired change form and a People log row that could not be written, and a success notice after a revoke.

## First-run setup

1. Start the console with `PULSE_API_URL` and an admin token (`PULSE_CONSOLE_ADMIN_TOKEN_FILE`). The token needs the `read` or `checks` scope and the `admin` scope of pulse-api, plus `incidents` for incident writes and `checks` for maintenance writes. `PULSE_API_URL` must be the final endpoint of pulse-api, because the console follows no redirect, and pulse-api answers must be uncompressed, because the console refuses compressed answers.
2. Find the setup code in the log: `docker logs <container> | grep 'setup code'`. The line is `pulse-console setup code: <code> (open /setup; a restart prints a new code)`. It is written to stdout outside the logger, so `PULSE_LOG_LEVEL` never hides it.
3. Open `/setup`, enter the code, then fill in the API URL, the owner email, name and password on `/setup/owner`. "Test connection" saves nothing; "Finish setup" tests again and saves. The test reads `GET /admin/config` and `GET /admin/tokens/self`; with a pulse-api older than the self route (`404`) it falls back to `GET /admin/tokens`, so older api versions still pass setup.
4. "Secure the owner account": Finish setup leads to `/account/authenticator`. Create a setup key, add it to an authenticator app (SHA-1, 6 digits, 30 seconds), and enter the code it shows. The answer lists ten recovery codes once; save them. This step cannot be skipped: until it is done, every protected page leads back to it, also after a new password sign-in.

Enrolment and TOTP need `PULSE_CONSOLE_SECRET_KEY_FILE`, a file with 64 lowercase hex characters that encrypts the TOTP seeds at rest (pulse-deploy generates it). Without it the console starts and logs a warning, but enrolment and TOTP sign-in answer `503`, so the owner gets no protected access. Recovery codes still work without it.

After setup the saved API URL is used. A different `PULSE_API_URL` logs one warning at start and is ignored. There is no way to change the saved URL yet.

**Owner recovery.** A lost Owner password (or a lost Owner second factor) is recovered from the container: `bun --no-env-file src/owner-reset.ts` (in the image `docker exec <container> bun --no-env-file src/owner-reset.ts`, in a deploy stack `docker compose -f <setup>/compose.yaml exec console bun --no-env-file src/owner-reset.ts`). It reads only `PULSE_CONSOLE_DB` and `PULSE_CONSOLE_PUBLIC_URL`, replaces any unused recovery link, and prints one line: `pulse-console owner reset link: <link> (valid 15 minutes, one use)`. Without a public URL the link is `/reset/<token>` and the line ends `; open it on the console address)`. Using the link sets a new password, ends every Owner session and removes the Owner's authenticator and recovery codes, so the next sign-in leads into enrolment. Before setup it exits `2` with `pulse-console: no owner account: finish setup first`. No page links to it. Another person's password is reset with a reset link from the Team page.

**Reset (destructive).** The last resort when the Owner recovery cannot run. Stop the console, delete the database file at `PULSE_CONSOLE_DB` with its `-wal` and `-shm` files (or the `console-data` volume), and start again. The console prints a new setup code.

The console stores only SQLite; Postgres and `DATABASE_URL` are not supported.

**Lost key.** Without the key file the stored seed cannot be read: TOTP sign-in answers `500` (`The authenticator secret cannot be read. Sign in with a recovery code.`). Sign in with the password and a recovery code, then replace the authenticator on `/account/authenticator`; the new seed is encrypted with the key in use. With the key and every recovery code lost, only the Owner recovery command (for the Owner) or the reset above helps.

**Sign out.** "Sign out" (`POST /sign-out`) ends only this browser. "Sign out all other sessions" (`/account/sessions/sign-out-all`) ends every other session of the account, also half-finished sign-ins and their pending setup keys, and keeps this browser signed in with the same cookie. After a suspected cookie theft, use both: first sign out all other sessions, then sign out. Replacing the authenticator also ends every other session. Changing your own password at `/account/password` also ends every other session and keeps this one.

**Known limits.** No passkeys yet. No QR code for the setup key. The throttles live in memory and a restart clears them. TOTP needs a correct clock (NTP) on the server and the phone: the console accepts one 30-second step before and after.

**Backup.** Back up the database file and the key file together. Copy the database file while the console is stopped, or use `sqlite3 console.db ".backup backup.db"` while it runs. On restore, remove any `-wal` and `-shm` files beside the restored file.

## Run locally

```sh
bun install --frozen-lockfile
PULSE_API_URL=http://localhost:3000 bun start
```

Open <http://127.0.0.1:8082>. Bun runs the TypeScript source directly (no build step).

## Run with Docker

```sh
docker build --tag pulse-console:local .
docker run --rm -p 127.0.0.1:8082:8082 -v console-data:/data -e PULSE_API_URL=http://api:3000 pulse-console:local
```

The image keeps its database at `/data/console.db`. `/data` is owned by `bun`; mount a volume there so the account survives a new container.

Released images are published as `ghcr.io/lorenzh/pulse-console` for `linux/amd64` and `linux/arm64`, with the tags `X.Y.Z`, `X.Y` and `X` (no `latest`):

```sh
docker pull ghcr.io/lorenzh/pulse-console:0.1.0
docker run --rm -p 127.0.0.1:8082:8082 -e PULSE_API_URL=http://api:3000 ghcr.io/lorenzh/pulse-console:0.1.0
```

Pin a setup to `X.Y.Z` by digest. How a release is cut and verified is in [docs/development.md](docs/development.md#releasing).

The image listens on `0.0.0.0:8082` inside the container and runs as the non-root user `bun`. It starts with `bun --no-env-file src/main.ts`, and its healthcheck also runs `bun --no-env-file`. So neither the console nor its healthcheck reads `.env` files, also not ones mounted into `/app`. Settings come from the container environment (`-e`, `docker run --env-file` read on the host, Compose `environment:` or `env_file:`). In the `full` setup of pulse-deploy ([`full/compose.yaml`](https://github.com/lorenzh/pulse-deploy/blob/main/full/compose.yaml), see [`full/README.md`](https://github.com/lorenzh/pulse-deploy/blob/main/full/README.md)) the console is published on host loopback only: host `127.0.0.1:${PULSE_CONSOLE_PORT:-8082}` maps to container port `8082`.

## Settings

| Setting                          | Default                        | Meaning                                                                                                                                      |
| -------------------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `PULSE_API_URL`                  | none, required                 | Base URL of pulse-api, `http` or `https`, without credentials, query or fragment.                                                            |
| `PULSE_CONSOLE_PORT`             | `8082`                         | Listen port.                                                                                                                                 |
| `PULSE_CONSOLE_HOST`             | `127.0.0.1` (image: `0.0.0.0`) | Listen address.                                                                                                                              |
| `PULSE_CONSOLE_PUBLIC_URL`       | unset (loopback mode)          | Public origin of the console; selects the mode `loopback`, `strict-https` or `strict-http`.                                                  |
| `PULSE_CONSOLE_DB`               | `./console.db`                 | Path of the SQLite database file; the image sets `/data/console.db`. `DATABASE_URL` is not read.                                             |
| `PULSE_CONSOLE_ADMIN_TOKEN`      | unset                          | Optional pulse-api admin token, at least 32 characters. Never logged.                                                                        |
| `PULSE_CONSOLE_ADMIN_TOKEN_FILE` | unset                          | File with the admin token (at least 32 characters), instead of the env var.                                                                  |
| `PULSE_CONSOLE_SECRET_KEY_FILE`  | unset                          | File with the 32-byte seed key as 64 lowercase hex characters. Without it TOTP answers `503`.                                                |
| `PULSE_CONSOLE_PROBE_API_URL`    | unset                          | Prefill of the probe API URL in Add location. http(s), no credentials, query or fragment, at most 2048 characters; one trailing `/` dropped. |
| `PULSE_CONSOLE_PROBE_IMAGE`      | unset                          | Prefill of the probe image. 1 to 255 characters of `[A-Za-z0-9._/:@-]`, first a letter or digit.                                             |
| `PULSE_CONSOLE_PROBE_NETWORK`    | unset                          | Prefill of the Docker network. `[A-Za-z0-9][A-Za-z0-9_.-]{0,127}`.                                                                           |
| `PULSE_LOG_LEVEL`                | `info`                         | `debug`, `info`, `warn` or `error`.                                                                                                          |

An invalid setting stops the start with exit code 2 and one line on stderr. Every rule and error text is in [docs/configuration.md](docs/configuration.md).

Every form POST can also answer `409` when its single-use form token is missing, expired or replayed.

`HEAD` works wherever `GET` does; another method on a known path answers `405` with `allow`. A finished setup starts an enrolment session and redirects to `/account/authenticator`. After setup an access gate sends a request without the needed session stage to its step: no session to `/sign-in?next=<path>`, a password-only session to `/sign-in/factor`, a user who must have a second factor (Owner, Admin, or everyone when the organisation switch is on) and has none to `/account/authenticator`. In loopback mode the app routes answer only a loopback `Host`. Every form POST checks `Origin` and a CSRF token. Cookies, modes, the POST order and the metrics are in [docs/configuration.md](docs/configuration.md). More in [docs/](docs/index.md).
