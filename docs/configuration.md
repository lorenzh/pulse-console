# Configuration

The console reads its settings from the environment once at start. An invalid setting stops the start with exit code 2 and one line on stderr, prefixed `pulse-console: `. The checks run in this order, and the first failure stops the start: `PULSE_LOG_LEVEL`, `PULSE_API_URL`, `PULSE_CONSOLE_PORT`, `PULSE_CONSOLE_HOST`, `PULSE_CONSOLE_PUBLIC_URL`, `PULSE_CONSOLE_DB`, the admin token, `PULSE_CONSOLE_SECRET_KEY_FILE`, `PULSE_CONSOLE_PROBE_API_URL`, `PULSE_CONSOLE_PROBE_IMAGE`, `PULSE_CONSOLE_PROBE_NETWORK`. `DATABASE_URL` is not read. A value that is blank or only whitespace counts as unset.

## Settings

| Setting                          | Default               | Rule                                                                                                                                                                                                                                   |
| -------------------------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PULSE_API_URL`                  | none, required        | Before setup the default of the setup form; after setup the saved URL wins. Trimmed. No whitespace or control character inside. Then `http:` or `https:`, a host, no credentials, no query or fragment. One trailing slash is dropped. |
| `PULSE_CONSOLE_PORT`             | `8082`                | Integer from 0 to 65535. `0` takes any free port.                                                                                                                                                                                      |
| `PULSE_CONSOLE_HOST`             | `127.0.0.1`           | Listen address. The image sets `0.0.0.0`.                                                                                                                                                                                              |
| `PULSE_CONSOLE_PUBLIC_URL`       | unset (loopback mode) | The console's public origin. The `PULSE_API_URL` rules, and no path other than `/`. Selects the mode, see below.                                                                                                                       |
| `PULSE_CONSOLE_DB`               | `./console.db`        | Path of the SQLite database file. Trimmed; blank counts as unset. The image sets `/data/console.db`.                                                                                                                                   |
| `PULSE_CONSOLE_ADMIN_TOKEN`      | unset                 | Optional. The token rules below.                                                                                                                                                                                                       |
| `PULSE_CONSOLE_ADMIN_TOKEN_FILE` | unset                 | Optional. Path to a file with the token; the content is trimmed, then the token rules apply.                                                                                                                                           |
| `PULSE_CONSOLE_SECRET_KEY_FILE`  | unset                 | Optional. Path to the key that encrypts TOTP seeds, see "Secret key" below.                                                                                                                                                            |
| `PULSE_CONSOLE_PROBE_API_URL`    | unset                 | Optional. Prefill of the probe API URL, see "Probe prefills" below.                                                                                                                                                                    |

| `PULSE_LOG_LEVEL`                | `info`                | `debug`, `info`, `warn` or `error`.                                                                                                                                                                                                    |

The URL texts are fixed: the value is never printed, so a password in the URL stays out of the output. Whitespace inside is refused before the URL parser runs, because the parser drops tabs and newlines and would accept `http://api\t:3000` as `http://api:3000`.

## Mode

`PULSE_CONSOLE_PUBLIC_URL` selects the mode:

- `loopback`: unset, or `http:` with the host `127.0.0.1`, `localhost` or `[::1]`.
- `strict-https`: an `https:` URL.
- `strict-http`: `http:` with any other host. The start logs `warn` `PULSE_CONSOLE_PUBLIC_URL uses http: session cookies are not marked Secure`.

In loopback mode every request outside the ops routes needs a `Host` of `127.0.0.1`, `localhost` or `[::1]`, with an optional port. Otherwise the answer is `421` `misdirected request: set PULSE_CONSOLE_PUBLIC_URL to serve this host`. This also stops DNS rebinding. A form POST needs `Origin: http://<Host>` in loopback mode and the public origin in the strict modes. A reverse proxy must keep the `Origin` header and serve the console from the origin in `PULSE_CONSOLE_PUBLIC_URL`.

## Setup code and API URL

At start, a database without a completed setup gets a new setup code: 16 random bytes, written as 8 groups of 4 lowercase hex characters. The console writes it once to stdout, outside the logger: `pulse-console setup code: <code> (open /setup; a restart prints a new code)`. Only its SHA-256 digest stays in memory. Spaces and `-` in the input are ignored and case does not matter. An empty code answers `422`; a wrong code answers `401` and counts. 5 wrong codes from one client in 15 minutes lock that client for 15 minutes (`429` with `Retry-After`). A restart makes a new code, drops the old code, all grants and the throttle state.

A correct code sets a setup grant cookie that is valid for 30 minutes. A new unlock replaces it. The grant opens only `/setup/owner`.

The setup form takes the API URL (the `PULSE_API_URL` rules, at most 2048 characters, one trailing `/` dropped, a path prefix kept), the owner email (trimmed, lowercased, 3 to 254 characters, one `@`), the name (1 to 100 characters) and the password (12 to 128 code points, not trimmed) twice. The connection test calls `GET <url>/admin/config` and then `GET <url>/admin/tokens/self` with the admin token, a 5000 ms timeout per call, a 5 MiB body cap and no redirects. A valid `/self` answer confirms the `admin` scope; its body is checked and dropped. Only a `404` on `/self` (a pulse-api older than the self route) makes the test fall back to `GET <url>/admin/tokens`: its `200` confirms the scope, and its `404` (an api without token routes) is accepted with a notice. Every other failure of either call keeps its fixed text. A compressed answer counts as a failed connection. It needs the `read` or `checks` scope and the `admin` scope. The connection test reads only the revision and the check ids of `GET /admin/config`, so it works with pulse-api before and after admin checks moved to its database. Finish setup saves the owner (argon2id hash) and the URL in one transaction, starts an `enrol` session for the owner and redirects to `/account/authenticator` (see "Second factor").

After setup the saved API URL is the one in use. A different `PULSE_API_URL` logs `warn` `PULSE_API_URL differs from the API URL saved at setup; the saved URL is used`, without a URL. The setup routes then answer `404`, also after a restart.

## Database

The console keeps its state in one SQLite file at `PULSE_CONSOLE_DB`. A new file is created with mode `0600`; an existing file is set to `0600`. SQLite gives the `-wal` and `-shm` files the same mode. The database uses WAL, foreign keys and a busy timeout of 5000 ms; its schema version is in `PRAGMA user_version` (now `3`). Migration 3 adds the role triggers (`invalid role` for a role outside `owner`, `admin`, `member`, `viewer`), `instance.require_2fa_all` (`0` or `1`, default `0`), and the tables `invites`, `reset_links` and `people_events`; `people_events` is append-only (`people_events is append-only` on an update or delete). No table uses `AUTOINCREMENT`. A schema-2 file keeps its users, sessions, authenticators and recovery codes. An older console stops on a schema-3 file; a downgrade needs a backup restore. Migration 2 adds the session `stage` and `next_path`, the tables `authenticators`, `pending_authenticators` and `recovery_codes`, and deletes every schema-1 session: those never had a second factor. The owner, the password hash and the API URL stay. A file that cannot be opened, is not a database or has a newer schema stops the start; it is never replaced by a fresh database. The database never holds the api token, a setup code or grant, a password or a plain session id. Postgres and `DATABASE_URL` are not supported (`DATABASE_URL` is ignored).

The start opens the database before it prints a setup code, so a database error never shows a code. Expired sessions are deleted at start and at every new session: full sessions 30 days after their last use, partial sessions and pending authenticators 900000 ms after creation.

Reset: stop the console, delete the file with its `-wal` and `-shm` files, and start again; this prints a new setup code. Backup: copy the file while the console is stopped, or run `sqlite3 <file> ".backup <copy>"`; remove `-wal` and `-shm` on restore.

## Admin token

The admin token is optional at start. Without it the setup page shows how to set it, and setup cannot complete. Set at most one of `PULSE_CONSOLE_ADMIN_TOKEN` and `PULSE_CONSOLE_ADMIN_TOKEN_FILE`. With `_FILE`, the console reads the named file once at start and trims its content; use it for Docker or Compose secrets.

When set, the value follows the api's admin token rules, so an accepted value can be an api admin token. The rules run in this order:

| Rule                                        | `PULSE_CONSOLE_ADMIN_TOKEN`                                                                           | `PULSE_CONSOLE_ADMIN_TOKEN_FILE=<path>`                       |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| both settings set                           | `set only one of PULSE_CONSOLE_ADMIN_TOKEN and PULSE_CONSOLE_ADMIN_TOKEN_FILE` (the file is not read) | same                                                          |
| file cannot be read                         |                                                                                                       | `PULSE_CONSOLE_ADMIN_TOKEN_FILE=<path>: cannot read (<code>)` |
| file is empty                               |                                                                                                       | `…: file is empty`                                            |
| one line                                    |                                                                                                       | `…: must hold one line`                                       |
| at least 32 characters                      | `PULSE_CONSOLE_ADMIN_TOKEN must hold at least 32 characters`                                          | `…: must hold at least 32 characters`                         |
| no whitespace                               | `PULSE_CONSOLE_ADMIN_TOKEN must not contain whitespace`                                               | `…: must not contain whitespace`                              |
| printable ASCII without space (`\x21-\x7e`) | `PULSE_CONSOLE_ADMIN_TOKEN must hold printable ASCII`                                                 | `…: must hold printable ASCII`                                |
| not starting with `replace-with-`           | `PULSE_CONSOLE_ADMIN_TOKEN still has the example placeholder`                                         | `…: still has the example placeholder`                        |
| not a public example token of the api       | `PULSE_CONSOLE_ADMIN_TOKEN is a public example token: generate your own`                              | `…: is a public example token: generate your own`             |

The token value and the file content never appear in a log line, an error, `/metrics`, the page or a response header. A file error names the path and the error code only. The start log line `pulse-console listening` carries `host`, `port`, the origin of the API URL in use, `hasAdminToken` (`true` or `false`), `hasSecretKey` (`true` or `false`), `mode` and `isSetUp`, and no other setting value.

## Secret key

`PULSE_CONSOLE_SECRET_KEY_FILE` names a file with the key that encrypts TOTP seeds at rest. The console reads it once at start, after the admin token. After dropping exactly one trailing `\n` it must hold exactly 64 lowercase hex characters (32 bytes), and it must differ from the admin token. The key is never stored in SQLite, logged or sent. Seeds are sealed with AES-256-GCM, a fresh 12-byte nonce, a 16-byte tag and the additional data `pulse-console:totp:v1:user:<user id>`, stored as `v1:<nonce>:<ciphertext>:<tag>` in base64url.

Unset: the start logs `warn` `PULSE_CONSOLE_SECRET_KEY_FILE is not set: authenticator enrolment and TOTP sign-in are unavailable`. Enrolment and a TOTP code then answer `503`; recovery codes still work. A seed that the key cannot open answers `500` (`The authenticator secret cannot be read. Sign in with a recovery code.`), logs `error` `authenticator secret cannot be decrypted` with `userId`, does not count as a failed guess and never changes the stored seed. Back up the database and the key file together.

## In the pulse Compose stack

In pulse-api's `compose.yaml`, `PULSE_CONSOLE_PORT` is also the Compose variable for the host port. Compose does not pass `.env` values into the container, so the container always listens on the image default `8082`, and the host port `${PULSE_CONSOLE_PORT:-8082}` on `127.0.0.1` is mapped to it. Compose sets `PULSE_API_URL: http://api:3000`. See the [pulse-api configuration](https://github.com/lorenzh/pulse-api/blob/main/docs/configuration.md).

## Image defaults

The image sets `NODE_ENV=production`, `PULSE_CONSOLE_HOST=0.0.0.0` and `PULSE_CONSOLE_DB=/data/console.db`, has a `/data` directory owned by `bun`, exposes `8082`, runs as the user `bun` and has a health check on `/healthz`. `bun start` outside the image listens on `127.0.0.1`.

## HTTP routes

The routes and their answers before and after setup are in the [README](../README.md#http-endpoints).

The path is the raw request target up to the first `?`, compared byte for byte. It is not decoded or normalised, so `/index.html`, `//healthz`, `/%2e%2e/`, `/./` and `/healthz/` are `404`. An unknown path answers `404` for every method; a known path with another method answers `405` with `allow` and an empty body. The ops routes `/healthz`, `/readyz` and `/metrics` accept `GET` and `HEAD` and every `Host`.

A form POST fails at the first broken rule, in this order: route and method (`404`, `405`); phase, a setup route after setup, or `POST /sign-in` or a second-factor or account route before it (`404`); the loopback `Host` (`421`); the access gate after setup (`303`, no body is read); `Origin` (`403`); a content type other than `application/x-www-form-urlencoded` (`415`); a body over 8192 bytes (`413`; `POST /checks/new` and `POST /checks/edit` allow 524288 bytes; `POST /status-page` allows 65536 bytes, `MAX_STATUS_FORM_BYTES`, and so do `POST /notifications/new` and `POST /notifications/edit`, `MAX_CHANNEL_FORM_BYTES`; the incident forms `POST /incidents/new`, `POST /incidents/update` and `POST /incidents/resolve` allow 32768 bytes; the maintenance forms `POST /maintenance/new` and `POST /maintenance/edit` allow 131072 bytes); a repeated known field or a bad list field (`400`, unknown fields are ignored; a route's list field, such as `component` or `check`, may repeat up to its limit of distinct values, and more values or one value twice answer `400`; `csrf`, `form_token` and every single field never repeat); the CSRF token (`403`, the session's token on routes behind the gate); the setup grant for `/setup/owner` (`403`); field format (`422`); the secret key (`503`); the throttle (`429`); verification (`401`); the connection test (`502`); state (`409`); the form token (`409`, see below); the commit (`200`, `303`, `409` or `500`).

`/metrics` has `pulse_up`, `pulse_console_http_requests_total` with the labels `path` (`/`, `/healthz`, `/readyz`, `/metrics`, `/setup`, `/setup/owner`, `/sign-in`, `/sign-out`, `/console.css`, `/console.js`, `/sign-in/factor`, `/account/authenticator`, `/account/security`, `/account/recovery-codes`, `/account/sessions`, `/account/sessions/sign-out-all`, `/team`, `/team/invites`, `/team/invites/revoke`, `/team/role`, `/team/remove`, `/team/reset-2fa`, `/team/transfer`, `/team/require-2fa`, `/team/reset-link`, `/account/password`, `/checks`, `/checks/check`, `/checks/shadowed`, `/checks/export`, `/checks/new`, `/checks/edit`, `/checks/delete`, `/invite/:token`, `/reset/:token`, `/fonts/:file` for the seven font routes, or `other`) and `code`, and `pulse_console_auth_attempts_total` with `kind` (`sign-in` for the password step, `setup-code`, `totp`, `recovery-code`, `enrolment`, `password-confirm`) and `result` (`success`, `failure`, `throttled`).

New log lines: `info` `setup complete` with `apiOrigin` and `checks`; `warn` `setup code refused` with `client` and `reason` (`credentials` or `throttled`); `info` `password accepted` with `userId` and `stage`; `warn` `sign-in failed` with `client` and `reason` (`credentials` or `throttled`); `info` `signed in` with `userId` and `factor` (`totp` or `recovery-code`, then also `remaining`); `warn` `second factor failed` with `client`, `kind` and `reason`; `warn` `password confirmation failed` with `client` and `reason`; `info` `authenticator confirmed` with `userId`; `info` `recovery codes created` with `userId`; `info` `signed out other sessions` with `userId` and `sessions` (the number of other session rows deleted); `error` `authenticator secret cannot be decrypted` with `userId`. `info` `form token refused` with `reason` (`replayed` or `invalid`) and `path`. No log line holds a password, an email, the token, a grant, a session id, a CSRF token, a seed, a setup key, a TOTP or recovery code, the secret key or the setup code or a form token.

Signed-in pages (`/`, `/checks`, `/checks/check`, `/checks/shadowed`, `/checks/export`, `/checks/new`, `/checks/edit`, `/checks/delete`, `/tokens`, `/tokens/new`, `/tokens/rotate`, `/tokens/revoke`, `/team`, `/team/invites`, `/team/invites/revoke`, `/team/role`, `/team/remove`, `/team/reset-2fa`, `/team/transfer`, `/team/require-2fa`, `/team/reset-link`, `/incidents`, `/incidents/manual`, `/incidents/automatic`, `/incidents/new`, `/incidents/update`, `/incidents/resolve`, `/incidents/delete`, `/maintenance`, `/maintenance/new`, `/maintenance/edit`, `/maintenance/delete` and, in a test-created server only, the routes under `/__test/`) run one fixed order: route and method (`404`, `405`); phase, before setup `GET` and `HEAD` `303` to `/setup` and `POST` `404`; the loopback `Host` (`421`); the full-session gate; for `POST` the `Origin`, content type, body size, repeated or list field and session CSRF checks above; the role (`403` shell page `Access denied`; the required role of each page comes from the policy in `src/permissions.ts`, see [team.md](team.md), and is read from the stored `users` row on every request); for `POST` the form token (`409`); the page. Without a live session any method answers `303` to `/sign-in?next=<target>`, where the target is the raw path and query when it is a safe path, else `/`. A `POST` without a session is not read and changes nothing; after sign-in the browser opens the page again with `GET`. An unknown path answers the `404` shell page `Page not found` only for a signed-in `GET` or `HEAD` after setup; its one title is the shell heading, followed by `There is no page at this address; go to the overview.` and a `Go to the overview` link to `/`; every other unknown-path request answers `404 not found`. `bun src/main.ts` never registers a `/__test/` route.

A team route with a target then runs in its handler: the id format of the query (`invite=<id>` or `user=<id>`, `^[1-9][0-9]{0,15}$`, else the shell `404`), the target lookup (`404`), the field format (`422`), the target rule (`403`), the `revision` (`<created_at>-<role>` of the person as shown; another value is `409` `Changed since you opened it`), the typed name or same-role check (`422`; a transfer to an Admin without an authenticator is `409`), the commit. Every team commit runs in one `BEGIN IMMEDIATE` transaction whose first step checks that the request's session row still exists; the dispatcher reads the body after the gate, so another request may have ended the session meanwhile. Then the answer is `409` shell page `Not saved` with `Your password or session changed while this was saved. Nothing was changed.` and a `Reload` link, and nothing changes. The commit then re-reads the actor's role (`403`), the target (`404`), its revision (`409`) and the target rule (`403`), all in the same transaction. One log line per committed change: `info` `team change` with `action`, `actorId` and `targetId`. A failed People-log insert rolls the change back, answers `500` `The change could not be saved.` and logs `error` `team change could not be saved` with the error name only.

The public invite link `/invite/<token>` matches only the raw path `/invite/` plus 43 characters of `[A-Za-z0-9_-]`; anything else is the plain `404`. Methods `GET`, `HEAD`, `POST` (else `405`). `GET`: phase (before setup `404`), the loopback `Host` (`421`), the link lookup (`404` `Link not valid`, no cookie), then the form, which sets the anonymous CSRF cookie and an `a:` form token bound to the raw link path. `POST`: phase, `Host`, `Origin` (`403`), content type (`415`), body size (`413`), repeated field (`400`), the anonymous CSRF cookie (`403`), the link lookup (`404`, before any password hash), field format (`422`), the form token (`409`: `Already submitted` with a link to `/sign-in`, else the form with `This form has expired. Send it again.`), the password hash, the commit. So a successful POST sent again answers `404`, not `409`. No step before the commit reads the session cookie; after a committed acceptance the new session replaces the row that the session cookie names. A refused form token on a link route logs `path` `/invite/:token`, never the token.

The reset link `/reset/<token>` follows the same rules and order (fields `password`, `password_confirm`), logs `/reset/:token`, answers `303` to `/sign-in?reset=done` and sets no session cookie.

Password work waits for an asynchronous hash, so writes that follow it are checked again in one `BEGIN IMMEDIATE` transaction. The password step of sign-in deletes the old cookie's row and expired rows, re-reads the user and inserts the session only when the stored hash is still the verified one; otherwise it writes nothing and answers `401` `Wrong email or password.`. New recovery codes, authenticator setup (`action=new`), sign out all and the own password change write only while the request's session row (and, after a password step, the verified hash) still exists; otherwise they answer `409` `Your password or session changed while this was saved. Nothing was changed.` and write nothing.

The Overview reads pulse-api on each visit: `GET <api>/admin/config` with `Authorization: Bearer <admin token>` and `GET <api>/checks` without it, started together, each with a 5000 ms timeout and no redirect followed. It always answers `200`. It shows the overall state and the count per check state as six linked tiles, in this order: Down (`/checks?state=down`), Degraded (`/checks?state=degraded`), Unknown (`/checks?state=unknown`), Maintenance (`/checks?state=maintenance`), Up (`/checks?state=up`) and Total (`/checks`, no filter). The five state tiles carry the state dot; Total has none. A tile with count `0` is still shown. A state tile counts the entries with that state in the one `/checks` answer of this visit; Total counts all its entries; shadowed definitions are not counted. A count can differ from the rows its link opens: the Checks list builds its rows from `/admin/config`, so a configured check with no `/checks` entry yet is a list row with state Unknown, and the unfiltered list also shows shadowed definitions (a state filter never shows them). The tiles fill a responsive grid; the number per row depends on the width. There are no tiles for `No checks yet` (zero checks, with a `Reload` link), `pulse-api cannot be reached` or `pulse-api sent an answer the console cannot use` for a failed read, a banner `pulse-api rejected the console token` for a `401`, or the no-token text without any request when no admin token is set. Each failed read logs one `warn` `api read failed` with `call` (`config`, `checks`, `export`, `uptime`, `results`, `latency` or `location-uptime`), `kind` and, for an HTTP answer, `status`; never a URL, body or token.

Every pulse-api read and write follows no redirect, so the API URL must be the final endpoint of pulse-api. pulse-api answers must be uncompressed: the console refuses an answer with a content encoding as a failed read or write, with the same fixed texts.

The Checks list at `/checks` reads the same two answers in the same way, validates `/admin/config` with the full check sources, and answers `200` with the same states; an api whose `/admin/config` lacks the sources shows `This pulse-api is too old for the Checks pages. It needs check sources (pulse-api with #565).` The export at `/checks/export` reads `GET <api>/admin/config/export` with the token (or `GET <api>/admin/config` for `?id=<id>&shadowed=1`) and answers `200` `application/json; charset=utf-8` with `content-disposition: attachment`, `cache-control: no-store` and the security headers; `HEAD` sends no body. A failed export read answers `502` with the state page; `call` is `export` for the export read. ## Form tokens

Every POST form carries a hidden `form_token` directly after `csrf`: 32 random bytes, base64url. A token is bound to its form's action path and to the client: `/setup`, `/setup/owner` and `/sign-in` bind it to the SHA-256 of the anonymous CSRF token, the sign-out form to the session. Second-factor, enrolment and account forms bind it to their current session as well. A `HEAD` request issues no token.

The token is used up at the commit point, after every other check of the route: before the grant of `POST /setup`, before the password hash of `POST /setup/owner` with `action=complete` (`action=test` does not use it), before the session of `POST /sign-in`, and before the session is deleted on `POST /sign-out`. On signed-in pages it is used up after the CSRF and role checks, before the page acts; a replay answers the `409` shell page `Already submitted`, an invalid token the page's form again with the kept input and `This form has expired. Your input is kept below. Send it again.` A refused request never uses up its token, and a failed sign-in still counts in the throttle.

- A token that was already used answers `409` `Already submitted` with a link to open the page again; nothing changes.
- A missing, unknown, expired or foreign token answers `409` with the form again, a fresh token and `This form has expired. Send it again.` (the owner form: `This form has expired. Your input is kept below. Send it again.` with the non-secret fields kept). Sign-in and the setup code release the throttle reservation, so this counts neither as a failure nor as a success.

On second-factor and account routes the form token is checked after credential verification, just before the mutation. An invalid token returns the form with a fresh token and the expired notice; the setup key is never redisplayed by a POST. A refused recovery-code form rolls back the transaction, leaving the code and partial session unused. A form-token refusal releases a factor throttle reservation. Authenticator replacement and recovery-code generation ask for the password again on retry. Sign out all also requires a form token (`409` if refused) and never touches the current session, including after a pause on the confirmation page.

Tokens live in memory for 12 hours (43200000 ms). The store keeps at most 100 unused tokens per client or session, 2000 pre-session entries and 8000 signed-in entries; a full pool drops its oldest entry, never one of the other pool. A restart drops every token, so an open form answers the expired `409` once and works again with its fresh token. After setup completes, the setup routes answer `404` before any token check.

## Sign-in and sessions

`POST /sign-in` takes `email`, `password` and an optional `next`. An empty field or a password over 128 code points answers `422` and does not count. A wrong password and an unknown email give the same `401` page (`Wrong email or password.`); an unknown email is verified against a dummy hash, so both take the same time. 5 failures in 15 minutes lock the account and, separately, the client address (the socket peer; forwarding headers are ignored) for 15 minutes: `429` with `Retry-After`. Success clears the account failures only. Each table holds at most 10000 keys.

A correct password deletes the old session of the browser and the expired rows, makes a new 32-byte session id and a CSRF token, and starts a session in the stage that the second-factor policy gives: `factor` (an authenticator exists, `303` to `/sign-in/factor`) or `enrol` (the owner has none, `303` to `/account/authenticator`). The Owner and every Admin must always have a second factor; when the Owner's organisation switch (`instance.require_2fa_all`) is on, every role must. A partial session stores `next` when it is a local path (it starts with one `/` that is not followed by `/` or `\`), else `/`, and the second factor redirects there. The database keeps only the SHA-256 digest of the session id. A session ends 30 days (2592000000 ms) after its last use; a request at least 60 seconds after the last use updates it and sends the cookie again with the same value. Sessions survive a restart. An invalid session cookie on `GET /sign-in` shows `Your session has expired.` and deletes the cookie. `POST /sign-out` needs the session's CSRF token and the form token; it deletes the row and the cookie. Without a session it checks `Origin` (`403`), content type (`415`), body size (`413`) and repeated fields (`400`); a form token already used on `/sign-out` then answers `409` `Already submitted`, anything else `303` to `/sign-in`. Nothing changes in either case.

## Second factor

Session stages: `factor` (password proven, second factor pending), `enrol` (password proven, no authenticator yet) and `full`. Only `full` opens protected pages. A partial session lives 900000 ms from creation, is never extended and its cookie has `Max-Age=900`. A `full` row of a user who must have a second factor (Owner, Admin, or any role with the switch on) and has no authenticator counts as `enrol` on its next request.

After setup every app route declares the stage it needs, and one gate checks it after the loopback `Host` and before `Origin` and the body. No session on a full or enrolment route: `303` to `/sign-in?next=<encoded path>`; no session on `/sign-in/factor`: `303` to `/sign-in`; a `factor` session elsewhere: `303` to `/sign-in/factor`; an `enrol` session elsewhere: `303` to `/account/authenticator`; a `full` session on `/sign-in/factor`: `303` to `/`. Before setup the gate does not run and the second-factor and account routes answer `404`.

TOTP: RFC 6238, HMAC-SHA-1, 6 digits, 30 seconds, T0 = 0. Steps `c - 1`, `c` and `c + 1` are accepted when they are above the stored last step; the lowest match is stored in the same transaction as the sign-in, so each code works once, also across browsers, restarts and a clock that goes back. Input is trimmed and spaces are removed; anything other than 6 digits, or a field over 64 characters, answers `422` and does not count. A seed is 20 random bytes; the setup key is its base32 text (32 characters, shown in groups of 4) with the `otpauth://` URI as text. Keep server and phone clocks in sync (NTP).

Recovery codes: ten distinct codes of 16 random bytes, shown once as 8 groups of 4 lowercase hex characters joined by `-`. Only the SHA-256 digest of each normalised code is stored. Input is trimmed, spaces and `-` removed and lowercased; anything but 32 hex characters answers `422`. A code replaces only the TOTP step, never the password. Its lookup, timing-safe comparison and use run in one `BEGIN IMMEDIATE` transaction, so one code works once, also in parallel.

`/sign-in/factor` takes `code` or `recovery_code` (exactly one, else `422` `Enter the code from your authenticator app or a recovery code.`). Order after CSRF: format (`422`), the key for a TOTP code (`503`), the factor throttle (`429`), verification (`401` `Wrong code.`), a decryption failure (`500`), commit (`303` with a new session id, or `303` to `/sign-in` when the factor session ended meanwhile).

`/account/authenticator`: `action=new` creates or replaces the pending setup key of this session (live 900000 ms). From a full session it needs the current password (`422` empty or over 128 code points, then `503` without the key, then the password throttle `429`, wrong `401`). `action=confirm` with `code`: format (`422`), key (`503`), factor throttle (`429`), a live pending key (else `409` `The setup key expired. Create a new one.`), the code (`401`). Success replaces the authenticator and the recovery codes, ends every session of the owner and starts a new full one for this browser in one transaction, and answers `200` with the ten codes and a "Continue" link.

`/account/security` (full session) shows when the authenticator was added, `<n> of 10 recovery codes left`, and links to "Replace authenticator", "New recovery codes" and "Sessions".

`/account/security`, `/account/sessions`, `/account/sessions/sign-out-all` and `/account/recovery-codes` render in the signed-in shell: the sidebar with "Signed in as", "Account security" and its one "Sign out" form, and the Main navigation, whose "Overview" link leads back to `/`. Every error re-render (`401`, `409`, `422`, `429`) keeps the shell. Sessions ends with "Back to account security"; the sign-out-all and new-codes confirmations have a Cancel link beside the primary button, to `/account/sessions` and `/account/security`. Cancel is a plain link and changes nothing. The recovery-code result keeps its single "Continue" link and has no Cancel. The header shows the e-mail in parentheses as one unit (`<span class="account-email">`): on a wide screen it moves to the next line whole and wraps inside only when it is wider than the line. On a wide screen the shell has a left sidebar whose border runs the full page height; its navigation and account part is sticky and scrolls on its own. At a viewport width of 719 px or less (`max-width: 719px`) the shell has a full-width header at the top, and the navigation is one horizontal row that scrolls sideways, with an icon beside each label. A focused link scrolls into view. Edge chevrons show that more links are off screen, in browsers with scroll-driven animations; other browsers show static edge shadows. Chevrons and shadows are hints, not buttons. The "Instance" group heading is hidden visually but stays for screen readers. In that mobile account row there is no avatar, the "Signed in as" prefix is hidden visually but stays in the markup, and name and e-mail stay on one line and end in an ellipsis when too long; the role, "Account security" and "Sign out" stay visible. Overview and Checks show for every role; Tokens, Probes and Team also for Admin and Owner. Incidents and Maintenance show for every role. Screens that do not exist yet (Activity, System) are not shown. Navigation visibility is not authorization: each route checks the role ([team.md](team.md)). Every ordinary link, visited or not, has the `--accent-text` color (`#7a4290` light, `#c29bd3` dark); a `:visited` rule never changes a link's color. The console follows the system light or dark color scheme.

`/account/recovery-codes`: `GET` shows the count left and a password form. `POST` follows the password rules of `action=new` (`422`, password throttle `429`, wrong `401`, none of them change the codes). Success replaces the whole set in one transaction and answers `200` with ten new codes; every old code stops working.

`/account/sessions` lists the live full sessions of the owner, newest last use first, with "Signed in" and "Last used" (`YYYY-MM-DD HH:MM UTC`) and "This browser" on the current one. Partial sessions are not listed, and the page holds no session id or token of another session. `POST /account/sessions/sign-out-all` needs the CSRF token of the current session (`403` otherwise, nothing changes). It runs `DELETE FROM sessions WHERE user_id = ? AND id_digest <> ?`: every other session of the owner goes, in every stage, and their pending setup keys go with them. The current row, cookie and CSRF token stay; no `Set-Cookie` is sent. The answer is `303` to `/account/sessions?signed-out=others`, which shows `All other sessions are signed out.` `POST /sign-out` ends only the current session. A later password change must call `deleteOtherSessions` in the transaction that writes the new hash.

The factor throttle is separate from the password throttle: 5 failures of TOTP, recovery codes and enrolment confirmation in 15 minutes lock the account and the client for 15 minutes (`429` with `Retry-After`). A correct password does not clear it; a successful second factor clears only the account failures.

Known limits: the setup, sign-in and factor throttles live in memory, so a restart clears them. There is no global cap on concurrent argon2id verifications; the throttle bounds them per account and client.

On `SIGTERM` or `SIGINT` the console turns not ready, stops accepting connections, closes idle ones and exits `0` after a clean stop. Open requests get 5000 ms; a stop that takes longer logs a warning and exits `1`.

| ----------------------- | -------------------- | --------------------------------------------------------------------- |
| `pulse_console_csrf`    | a GET of a form page | none                                                                  |

## Security headers

Every response, including ops routes, `404` and `405`, carries:

- `content-security-policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`
- `x-content-type-options: nosniff`
- `x-frame-options: DENY`
- `referrer-policy: same-origin`: a browser sends the real `Origin` on a same-origin form POST, and no referrer to another origin. With `no-referrer` a browser sends `Origin: null`, which the Origin check refuses.

Pages also carry `cache-control: no-store`. They load `/console.css`; setup and sign-in have no script. Signed-in shell pages load the one script `<script src="/console.js" defer></script>`, served with `text/javascript; charset=utf-8`. There is no inline script or style and no external asset. The seven fixed font routes `/fonts/space-grotesk-latin-{400,500,600,700}-normal.woff2` and `/fonts/jetbrains-mono-latin-{400,500,600}-normal.woff2` answer `GET` and `HEAD` before and after setup with `font/woff2` and `cache-control: public, max-age=31536000, immutable`; every other response keeps `no-store`. Any other `/fonts/` path is `404`. The license texts are not served.

`/console.js` is a progressive enhancement of submit buttons. On submit of a POST form it marks the form busy and cancels a second submit of it; after the browser built the form data it disables the form's submit buttons, sets `aria-busy="true"` and shows the `data-busy-label` text on the pressed button. A page restored from the back/forward cache is usable again. Without JavaScript every form works by native submit and the button stays enabled; the form token still refuses a second effect.

## Owner recovery command

`bun --no-env-file src/owner-reset.ts` reads only `PULSE_CONSOLE_DB` (default `./console.db`) and `PULSE_CONSOLE_PUBLIC_URL`, with the rules and error texts of the console; it needs neither `PULSE_API_URL`, the admin token nor the secret key. It opens the database with the same file mode and migrations. Before setup, or without an Owner row, it exits `2` with `pulse-console: no owner account: finish setup first`; a setting or database error exits `2` with `pulse-console: <message>`. Otherwise one transaction deletes the unused `owner-recovery` links, inserts a new one (`expires_at = created_at + 900000`, `issued_by` null, stored only as its SHA-256 digest) and writes `owner.recovery-link` with actor `container`; then it prints `pulse-console owner reset link: <link> (valid 15 minutes, one use)` and exits `0`. Without a public URL `<link>` is `/reset/<token>` and the line ends `(valid 15 minutes, one use; open it on the console address)`. The link is redeemed at `/reset/<token>` in the order above; it also deletes the Owner's authenticators, recovery codes and pending setup keys, ends every Owner session and writes `owner.recover` (value `owner-recovery`).


## Probe prefills

`PULSE_CONSOLE_PROBE_API_URL`, `PULSE_CONSOLE_PROBE_IMAGE` and `PULSE_CONSOLE_PROBE_NETWORK` are read after `PULSE_CONSOLE_SECRET_KEY_FILE`, in that order. They use the rules of the add-location fields `api_url`, `image` and `network`. A blank value counts as unset, and the API URL loses one trailing `/`. An invalid value stops the start with exit code 2; the line names the setting and its rule, never the value. They are prefills only: the person sees and can change every value before a probe token is created. The console never copies its own `PULSE_API_URL` into a probe snippet. The heartbeat line of a check detail never holds the saved API URL either: it shows `<pulse-api-url>` for the person to replace.
